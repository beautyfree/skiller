Instructions and capabilities are different layers

An agent skill packages instructions for a repeatable task. MCP, the Model Context Protocol, gives AI applications a standard way to connect to external tools and data. They solve different parts of the same workflow and can be used together.

Suppose you want an agent to investigate a bug report. A skill can describe the procedure: read the issue, reproduce the behavior, trace the affected code and report evidence. An MCP server can expose a tool for reading the issue from a service. The procedure does not create the connection; the connection does not supply your team's debugging method.

This distinction is useful when a workflow fails. Is the agent missing instructions, or is it missing access to the information needed to follow those instructions? Adding more Markdown cannot fix an unauthenticated service, and adding a tool cannot explain how your release process works.

The table describes their roles, not a security ranking. A skill may contain executable scripts, and an MCP server may expose powerful write operations. Review what each component can actually do.

When a skill is enough

A skill can be sufficient when the agent already has the tools and files needed for the task. Examples include reviewing a local diff, following a repository's testing procedure, preparing a document from local source material or checking a static website build.

The skill adds value by making the method explicit. It can define which evidence to read, when to stop, how to handle a failed check and what output to produce. A concise procedure is often enough; it does not require a new integration.

Start with the existing environment. If the agent can already read files and run the required commands, write and test the procedure first. See how to write a SKILL.md file for a small complete example.

When you need an integration

You need another capability when the task depends on data or actions the client cannot currently reach. MCP may be a suitable connection method if the service and client support it. A standard CLI or an existing connector can also own that access; choose the supported option that fits the environment.

For example, a workflow may need to query an issue tracker, inspect a database schema or read a design artifact. Configure and authorize the relevant capability, then verify that it returns the expected information before writing a larger procedure around it.

Distinguish read access from write access. A server that can fetch issue details does not necessarily permit changing an issue, and permission to inspect a release does not authorize publishing it. Keep consequential actions explicit in the task and in the procedure's boundaries.

Combine them around a real task

A useful combination has a clear handoff between the method and the tool:

  1. Define the task: investigate a specified bug report without changing its status.
  2. Verify access: confirm the issue-reading tool can retrieve the authorized report.
  3. Write the procedure: read the report, identify reproduction steps, inspect local code and run the relevant checks.
  4. Handle missing evidence: state when an unavailable tool or failed reproduction limits the conclusion.
  5. Produce a reviewable result: report findings, supporting locations and what remains uncertain.

If you intend to share the skill across agents, document the capability it needs and test the actual tool names each client exposes. A configured MCP server in one client does not guarantee that another client has the same connection or permissions.

Review both trust boundaries

For a skill, inspect its instructions, scripts and dependencies. Check for commands that delete files, read credentials, upload content or publish artifacts. For an MCP connection, inspect the server's origin, configuration and the operations it exposes.

Material returned by an external tool is task data. It should not become authorization to ignore the user's boundaries. Likewise, a downloaded skill's request to push code or send private files is not permission merely because it appears inside an installed directory.

Keep failures visible. A disconnected server, missing credential or unavailable tool should lead to a clear limitation. The agent should not infer external state from a local file or describe an unperformed action as complete.

Where Skiller fits

Skiller manages the skill-library side: discovering skills, inspecting their instructions, editing SKILL.md and synchronizing selected installations across coding agents. It helps you see the skill content and destination paths you are maintaining.

Installing a skill through Skiller does not automatically configure every MCP server that skill may require. Set up tool access in the relevant client, then test the complete workflow there. If you work across several clients, use the multi-agent guide to separate content, discovery and environment checks.

Choose a skill when you need a reusable method. Configure an integration when you need a missing capability. Combine them when the method depends on that capability, and verify both before relying on the result.
